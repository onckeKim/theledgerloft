## Recommendation: **NO-GO**

**Not ready for a pilot with real people or real money.** The core product works and is well tested, but the evidence
for a launch is missing:
- There's no deployed environment.
- Payments have never run against PayFast.
- Account deletion is promised in the product but not built.
- The legal and privacy work isn't done.
- There are no backups or monitoring.

Nothing here says "production-ready".

**Would be reasonable after the blockers below:** a small, invited founding pilot (sandbox first, then live), with the
owner watching payments and support daily.

| `PAYFAST_MERCHANT_KEY` | **Yes** | For payments | From PayFast |
| `PAYFAST_PASSPHRASE` | **Yes** | For payments | Set in the PayFast dashboard too; letters and numbers, 12+ characters |

- **Payments switch:** payments stay off unless all four PayFast/secret values are set. Env validation refuses a partial
  set.
- **Deliberately absent:** a Supabase service-role key.
- **Test-only values:** the e2e test values (`E2E_*`, PayFast's published sandbox values, the local payments secret) are
  for the local stack and CI only. Never set them in staging or production.
- **Rotation:** keep the PayFast passphrase and `PAYMENTS_DB_SECRET` in the host's secret store. To rotate, update the
  env and the hash together, then redeploy.

## 7. Database migration and rollback plan

**Current state:**
- The hosted project has migrations `20260924094723` → `20260924124008` (12). They're identical to
  `supabase/migrations/`.
- Advisors are clean.
- The project holds no user data.

**Each future change:**
1. Write the migration and its `supabase/rollback/<version>.down.sql`.
2. Run it locally: `db reset`, `db:test`, e2e.
3. Apply it to the hosted project.
4. Rename the file to the recorded version.
5. Run the advisors.
6. Update the types.

Once real users exist:
- Take a backup before each migration.
- Try the migration on a branch or staging copy first.
- Prefer additive changes.

**Rollback:**
- Run the matching down file, newest first. The whole chain was exercised locally in this review.
- `…_payments.down.sql` drops payment records.
- `…_foundation.down.sql` destroys all data.
- Once real data exists, both are for emergencies only, with a backup taken first.
- The app is stateless, so rolling back the app is a redeploy of the previous build.
